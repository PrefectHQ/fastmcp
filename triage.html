A run status is only part of the result

Execution, delivery, freshness, and acceptance answer different questions. One cannot stand in for the others.

Signal What it tells you What to check next
Completed The selected, bounded work finished. Read its findings and public receipts. This does not mean a fix was merged or the backlog is empty.
Degraded The workflow retained an operational problem or a stale result at its final check. Check what was already published, what stopped, and whether the cause needs a refresh or a repair.
Failed / Crashed Execution itself did not finish normally. Inspect the error and retained evidence. Check GitHub before retrying an uncertain write.
Awaiting a maintainer A proposal or contribution needs a human decision. Review its evidence and remaining gates. A pending decision alone is not an execution failure.

In the current Prefect workflow, Degraded is a custom name on a Completed state. It records a business outcome that needs attention, even though the flow reached its end. This label can therefore coexist with a successfully posted review.

Who is responsible for what?

FastMCP uses more than one automation system. Their responsibilities and permissions matter.

G

GitHub Actions

Applies labels, enforces contribution gates, and runs the existing duplicate-marking and closure cooldowns.

Those existing closers retain their own rules for human comments and objections.

P

Prefect triage

Assesses selected issues, reproduces behavior, verifies existing contributions, and obtains an independent review.

Configured publication can post review comments or publish validated fixes as draft PRs.

✓

Maintainers

Decide contributor assignments, contribution readiness, supported behavior, and what gets merged.

Assignment, finishing, and closure recommendations from triage require approval.

A bot review is a comment, not merge approval.

The dedicated reviewer App posts findings against a recorded PR head. The triage path does not automatically merge PRs or execute its assignment and closure proposals. Existing GitHub duplicate-closing automation is a separate lifecycle.

Why work can stop

Stopping can protect a contributor or prevent an outdated action. An operational defect can also stop useful work.

Reasons to recheck the decision

  • A new commit or substantive review finding changes the evidence.
  • A contributor claims the work, or a maintainer changes direction.
  • An author adds a hold, closes the contribution, or withdraws it.
  • A security concern requires restricted review.

Problems in the automation

  • A worker cannot execute or required evidence cannot be loaded.
  • A GitHub write has an uncertain outcome and needs readback.
  • A freshness check mistakes the bot’s own publication effects for new evidence.

The #5588 example documents that last defect. It is a limitation of the workflow, not a contributor error.

Reading a triage result

  1. Find the output. Is there an actual review, a draft PR, a recommendation, or only retained evidence?
  2. Check the revision and limitations. What code was tested? Did the checks execute? Has relevant evidence changed?
  3. Identify the next owner. Does a maintainer need to decide, a contributor need to finish a change, or an operator need to repair the workflow?
  4. Count acceptance later. A posted review or draft is an output. A merged fix or an approved action is a separate outcome.

This is a static explanation of recorded behavior, not a live health dashboard. The triage design is under review; the examples preserve both useful outputs and known failures.
