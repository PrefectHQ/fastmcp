The Python controller owns the write paths

The graph above ends after retaining evidence. The controller claims each issue before invoking it, then reads the result and chooses the next action.

Existing PR
Independent triage review → freshness check → reviewer App posts a GitHub COMMENT review.
Reproduced issue, fix mode
Prepare patch → validate the exact candidate → independent patch review → publication preflight → draft PR. Failed validation or requested changes can return to preparation once.
Held work or a maintainer decision
Retain the reason or proposed action. Assignment, closure, and finishing recommendations await approval. This path does not merge PRs.
Intake completion
Check freshness again and commit processed/pending state. Operational records or stale evidence can produce Completed(name="Degraded").

What “Degraded” meant in the recent run

The review posted. The final check invalidated it.

The App’s review on PR #5588 mentioned related issues and PRs. GitHub added four cross-reference events. The final intake check treated those events as new evidence and left the issue pending.

That is a freshness-check defect. It did not undo the review. The label also covers operational failures, so the word alone cannot tell you which step stopped.
