MCP Events let a client subscribe to things that happen in your application. For example, a build server can publish a `build.finished` event whenever a build completes. A dashboard can subscribe to update its status display, and a coding agent can subscribe to investigate failed builds. Both can receive results for builds started by someone else.

An event can come from your application at the moment it happens, or from the history another system already keeps. Both sources look the same to a subscriber. The client can poll for changes or receive events on an open stream. Webhook delivery adds a third option for clients that can receive HTTP callbacks. See [delivery modes](#delivery-modes) for examples of each.

<Note>
FastMCP's implementation of the [MCP Events extension](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415) is experimental. Its API may change without a deprecation period.
</Note>

## Publishing events

Install the Events package on the server and on each Python client that subscribes. The `events` extra installs it alongside FastMCP.

```bash
pip install "fastmcp[events]"
```

Register an `EventsExtension` on the server, then declare an **event type** with `@events.event`. The name is what clients subscribe to, the model's docstring describes when the event occurs, and its fields describe the payload. Calling `emit()` with one instance records one occurrence. In this example a tool reports the result of a build. In a CI integration, the code that learns the build has finished can call the same method.

```python server.py
from pydantic import BaseModel

from fastmcp import FastMCP
from fastmcp_events import EventsExtension

mcp = FastMCP("Builds")
events = EventsExtension()
mcp.add_extension(events)


@events.event("build.finished")
class BuildFinished(BaseModel):
    """A build reached its final status."""

    build_id: str
    repo: str
    status: str


@mcp.tool
async def finish_build(build_id: str, repo: str, status: str) -> str:
    build = BuildFinished(build_id=build_id, repo=repo, status=status)
    await events.emit(build, event_id=build_id)
    return f"Recorded build {build_id}"
```

An event ID identifies one occurrence. Here each build finishes once, so a retry can use the same build ID. If a build can finish more than once, use an ID for each attempt. When you omit `event_id`, FastMCP assigns one at emit time.

## Subscribing to events

Start the example server over HTTP so the subscriber and the process reporting the build connect to the same running server.

```bash
fastmcp run server.py --transport http
```

In a second terminal, list the event types and start watching for completed builds. A new subscription starts at the current position. Leave the watch running while you report a build.

```bash
fastmcp experimental events list http://localhost:8000/mcp
fastmcp experimental events watch http://localhost:8000/mcp build.finished --count 1
```

From a third terminal, report a completed build. The caller receives `Recorded build ci-42`. The subscriber receives a `build.finished` event with the ID `ci-42` and the build payload, then exits after that one event. The [CLI reference](/cli/client#watching-events) covers JSON output and resuming a watch.

```bash
fastmcp call http://localhost:8000/mcp finish_build build_id=ci-42 repo=api status=passed
```

### Python clients

Pass `EventsClientExtension()` to `Client` to opt into Events. FastMCP serves Events on connections using the 2026-07-28 MCP protocol. The Events package provides functions that take the connected client. `list_events()` returns the event types with their descriptions, subscription arguments, payload schemas, and available delivery modes. `subscribe_events()` returns an async iterable of occurrences. Run this client in place of the terminal watch, then report another build.

```python watch.py
import asyncio

from fastmcp import Client
from fastmcp_events import EventsClientExtension, list_events, subscribe_events


async def main() -> None:
    extensions = [EventsClientExtension()]
    async with Client("http://localhost:8000/mcp", extensions=extensions) as client:
        for event_type in await list_events(client):
            print(event_type.name, event_type.delivery)

        builds = subscribe_events(client, "build.finished")
        async for build in builds:
            print(build.event_id, build.data["status"])


if __name__ == "__main__":
    asyncio.run(main())
```

### Filtering subscriptions

The build server above sends every completed build to anyone watching `build.finished`. A dashboard for a single repository may only want that repository's builds. To let the subscriber choose, replace the `BuildFinished` definition in `server.py` with the following version. The tool still emits each build once.

```python
@events.event("build.finished")
class BuildFinished(BaseModel):
    """A build reached its final status."""

    build_id: str
    repo: str
    status: str

    def for_subscription(self, repo: str | None = None) -> "BuildFinished | None":
        if repo is None or self.repo == repo:
            return self
        return None
```

The `repo` **field** is part of the event payload. The `repo` **parameter** of `for_subscription` becomes a subscription argument that clients discover through `list_events()`. FastMCP validates the arguments, then calls the method with a fresh copy of each event. Returning the event delivers it to that subscriber. Returning `None` skips it and advances the subscriber's read position. You can also return a modified copy to change what the subscriber sees. The method runs synchronously during delivery, so keep I/O in the event source.

Restart the server with this definition. A client that omits `repo` still gets every build. In `watch.py`, passing `{"repo": "api"}` as the third argument to `subscribe_events()` selects only the `api` repository. You can try the same filter from the CLI, then call `finish_build` for two different repositories to see which one reaches the watch.

```bash
fastmcp experimental events watch http://localhost:8000/mcp build.finished repo=api
```

### Resuming from a cursor

A **cursor** identifies how far the subscription has read. Save `builds.cursor` after processing an event and pass the saved value as `cursor=` when subscribing again to the same event type with the same arguments. Treat the value as opaque. With no saved cursor, the first read establishes a starting position and skips earlier history.

The cursor advances by batch. If you stop midway through a batch, resuming can deliver some occurrences again. A running subscription remembers the last 1,024 event IDs it has yielded. A new subscription starts with an empty history, so use stable event IDs to recognize repeats when processing an event has lasting effects. If the source has lost part of the requested history, the subscription sets `truncated` to `True` and continues with the events still available.

## Delivery modes

The server advertises delivery modes for each event type. The example server offers both `poll` and `push`. Two clients can subscribe to the same `build.finished` events using different modes. If you leave the choice to `subscribe_events()` or the CLI, FastMCP prefers push and falls back to polling when the server only offers polling or refuses a stream as unsupported.

### Polling (pull)

With polling, **the client asks for new events**. Its first `events/poll` request establishes a cursor. Each subsequent request sends that cursor back and receives a batch of newer events and the next cursor. Each request finishes, so polling works on hosts with short request timeouts and fits clients that run periodically.

A scheduled job can make one poll per run with `poll_events_mcp()`. Run `python poll_builds.py` once against the example server to save the starting cursor. Call `finish_build` while the client is offline, then run the script again from the same directory. It prints the builds recorded since its last run and saves the new cursor after processing the batch.

```python poll_builds.py
import asyncio
from pathlib import Path

from fastmcp import Client
from fastmcp_events import EventsClientExtension, poll_events_mcp


async def main() -> None:
    checkpoint = Path("build-finished.cursor")
    cursor = checkpoint.read_text() if checkpoint.exists() else None
    extensions = [EventsClientExtension()]

    async with Client("http://localhost:8000/mcp", extensions=extensions) as client:
        batch = await poll_events_mcp(client, "build.finished", cursor=cursor)

    if batch.truncated:
        print("Some earlier builds are no longer available.")
    for build in batch.events:
        print(build.event_id, build.data["status"])
    if batch.cursor is not None:
        checkpoint.write_text(batch.cursor)


if __name__ == "__main__":
    asyncio.run(main())
```

For a continuous watch, `subscribe_events(client, "build.finished", delivery="poll")` runs the loop and advances the cursor for you. It reads the next batch immediately while there is a backlog. Once caught up, it waits for the server's suggested interval, which defaults to 30 seconds. The equivalent CLI watch stops after the first build it receives.

```bash
fastmcp experimental events watch http://localhost:8000/mcp build.finished --delivery poll --count 1
```

Set the server's suggested interval with `EventsExtension(poll_interval_ms=...)`. A reader can override it for one batch with `EventBatch(next_poll_ms=...)`.

### Push

With push, **the client opens a stream and the server sends events on it**. One `events/stream` request stays open for the subscription. When the build server calls `emit()`, the waiting client receives the build immediately. For an event backed by a reader, the server checks the upstream on its poll interval and sends new occurrences over the same stream. Heartbeats tell the client the stream is still open during quiet periods.

A live dashboard can require push by passing `delivery="push"` to `subscribe_events()`. Run `python stream_builds.py`, leave it running, and call `finish_build` from another terminal. The loop waits on the open stream. Each time a build arrives, it prints the result and waits for the next one.

```python stream_builds.py
import asyncio

from fastmcp import Client
from fastmcp_events import EventsClientExtension, subscribe_events


async def main() -> None:
    extensions = [EventsClientExtension()]
    async with Client("http://localhost:8000/mcp", extensions=extensions) as client:
        builds = subscribe_events(client, "build.finished", delivery="push")
        async for build in builds:
            print(build.event_id, build.data["status"])


if __name__ == "__main__":
    asyncio.run(main())
```

To open the same stream from the terminal and exit after one build, use the CLI watch with `--delivery push`.

```bash
fastmcp experimental events watch http://localhost:8000/mcp build.finished --delivery push --count 1
```

Push requires a host that can keep a response open. On a host that buffers responses, or an HTTP app using `json_response=True`, register `EventsExtension(push=False)` so clients discover polling from the start.

A dropped push stream can reopen from its cursor while the client session is healthy. The client retries up to four consecutive times with backoff and also retries a stream that goes silent for three heartbeat intervals. If the session itself ends, open a new client and subscribe with the saved cursor. If a slow consumer overflows its push buffer, the iterator raises `EventBacklogFullError`. Resume with `delivery="poll"` and a bounded `max_events` to drain the backlog in smaller batches.

### Webhook

With webhook delivery, the client registers an HTTPS callback and can then disconnect. When a build finishes, the MCP server sends a signed POST to that callback. This suits a hosted automation that can receive HTTP requests even when the process that registered the subscription is offline.

#### Enable delivery on the server

The server opts in with `WebhookDelivery()`. Subscriptions belong to the authenticated caller, so the server also needs an [authentication provider](/servers/auth/authentication). To adapt the build example, replace the imports and setup in `server.py` above `@events.event("build.finished")` with this block. This example reads a test bearer token from `BUILDS_TOKEN`. Set it on both the MCP server and the subscribing client.

```python
import os

from pydantic import BaseModel

from fastmcp import FastMCP
from fastmcp.server.auth.providers.jwt import StaticTokenVerifier
from fastmcp_events import EventsExtension, WebhookDelivery

auth = StaticTokenVerifier(tokens={
    os.environ["BUILDS_TOKEN"]: {"client_id": "build-dashboard", "scopes": []}
})
mcp = FastMCP("Builds", auth=auth)
events = EventsExtension(webhooks=WebhookDelivery())
mcp.add_extension(events)
```

Restart the build server. It now advertises `webhook` alongside `poll` and `push`. Webhook delivery reads from a saved position between POSTs. Emitted events already have a cursor. If you use a reader, it must return a resumable cursor too.

#### Receive signed requests

Start the receiver before registering the subscription. On registration, the MCP server sends a signed verification challenge to confirm that the endpoint controls the signing secret. Generate the secret once with `fastmcp_events.new_webhook_secret()` and set the resulting value as `WEBHOOK_SECRET` on the receiver and the subscribing client. The bearer token authenticates the client to MCP. The signing secret lets the callback authenticate incoming deliveries.

This Starlette endpoint passes the raw request body and headers to `verify_webhook()`, which checks the signature and timestamp before returning the decoded message. It echoes the challenge on registration, prints the result for each build, and handles notices about gaps or termination separately.

```python receiver.py
import os

from starlette.applications import Starlette
from starlette.requests import Request
from starlette.responses import JSONResponse, Response
from starlette.routing import Route

from fastmcp_events import WebhookVerificationError, verify_webhook

secret = os.environ["WEBHOOK_SECRET"]


async def receive_build(request: Request) -> Response:
    try:
        message = verify_webhook(secret, request.headers, await request.body())
    except WebhookVerificationError:
        return Response(status_code=401)

    kind = message.get("type")
    if kind == "verification":
        return JSONResponse({"challenge": message["challenge"]})
    if kind == "gap":
        print("Build history has a gap", message["cursor"])
    elif kind == "terminated":
        print("Subscription ended", message["error"])
    else:
        print(message["eventId"], message["data"]["status"])
    return Response(status_code=204)


app = Starlette(routes=[Route("/builds", receive_build, methods=["POST"])])
```

Serve the app at an HTTPS address reachable from the MCP server and set `BUILDS_CALLBACK_URL` to the full URL ending in `/builds`. By default the server requires a public address and does not follow redirects. For local testing, `WebhookDelivery(allow_private_addresses=True)` permits private and loopback addresses. HTTPS is still required.

#### Subscribe from Python

Set `BUILDS_MCP_URL` to the authenticated server's MCP endpoint. Run this client once. When the receiver answers the challenge, `subscribe_webhook()` returns the lease deadline. After this script exits, call `finish_build` with the server's bearer token. The receiver prints the event ID and build status.

```python subscribe_builds.py
import asyncio
import os

from fastmcp import Client
from fastmcp_events import EventsClientExtension, subscribe_webhook


async def main() -> None:
    async with Client(
        os.environ["BUILDS_MCP_URL"],
        auth=os.environ["BUILDS_TOKEN"],
        extensions=[EventsClientExtension()],
    ) as client:
        lease = await subscribe_webhook(
            client,
            "build.finished",
            url=os.environ["BUILDS_CALLBACK_URL"],
            secret=os.environ["WEBHOOK_SECRET"],
        )
    print("Renew before", lease.refresh_before)


if __name__ == "__main__":
    asyncio.run(main())
```

To keep receiving builds, call `subscribe_webhook()` again before `refresh_before` with the same identity, event name, arguments, and URL. A live lease retains its delivery position. Persist the cursor from each successfully processed event and pass it as `cursor=` to resume if the lease lapses. To stop immediately, call `unsubscribe_webhook()` with the same client identity, event name, arguments, and URL.

#### Delivery and retries

By default, `WebhookDelivery` grants a one-hour lease. Clients can request a duration with `ttl_ms`. The server bounds it with `min_ttl` and `max_ttl`, which default to one minute and one hour. An emit wakes the sender in the same process. Otherwise the sender checks for work every five seconds (`interval`).

The server retries transient delivery failures with backoff for up to `retry_window` (ten minutes by default) before moving past the event. The same delivery has the same `webhook-id` header across retries and replicas. A receiver that triggers a lasting action, such as opening an incident, should use that ID to recognize repeated deliveries.

## Reading from an upstream

If your application already records events in a database or an event log, it can serve that history directly. Register a **reader** for the event type. FastMCP passes it an `EventPoll` containing the client's cursor and validated subscription arguments. The reader returns an `EventBatch` containing the occurrences it found and the position to read from next. Each event type has one source, so choose a reader for a type whose history belongs to the upstream, or `emit()` for one whose history FastMCP keeps.

### A database-backed reader

Suppose a mail service appends deliveries to a SQLite table. Its integer primary key gives each delivery a stable ID and a position that survives an MCP server restart. To try this example locally, create the table in the directory where you'll run the server.

```bash
sqlite3 mail.db 'CREATE TABLE deliveries (id INTEGER PRIMARY KEY, sender TEXT NOT NULL, received_at INTEGER NOT NULL DEFAULT (unixepoch()))'
```

On the first read, return the newest ID and an empty batch so the subscription starts from now. On subsequent reads, fetch rows after that ID in order. This reader fetches one extra row to find out whether more results are waiting.

```python mail_server.py
import sqlite3
from contextlib import closing
from datetime import UTC, datetime, timedelta

from pydantic import BaseModel

from fastmcp import FastMCP
from fastmcp_events import Event, EventBatch, EventPoll, EventsExtension

mcp = FastMCP("Mail")
events = EventsExtension()
mcp.add_extension(events)


@events.event("email.received")
class EmailReceived(BaseModel):
    """A message arrived in the inbox."""

    sender: str


@events.reader(EmailReceived)
def read_deliveries(poll: EventPoll) -> EventBatch:
    with closing(sqlite3.connect("mail.db")) as db:
        if poll.cursor is None:
            query = "SELECT COALESCE(MAX(id), 0) FROM deliveries"
            (newest,) = db.execute(query).fetchone()
            return EventBatch(cursor=str(newest))

        limit = min(poll.max_events or 100, 100)
        rows = db.execute(
            "SELECT id, sender, received_at FROM deliveries "
            "WHERE id > ? ORDER BY id LIMIT ?",
            (int(poll.cursor), limit + 1),
        ).fetchall()

    cutoff = None
    if poll.max_age_ms is not None:
        cutoff = datetime.now(UTC) - timedelta(milliseconds=poll.max_age_ms)

    cursor = poll.cursor
    truncated = False
    messages = []
    for row_id, sender, received_at in rows[:limit]:
        cursor = str(row_id)
        timestamp = datetime.fromtimestamp(received_at, UTC)
        if cutoff is not None and timestamp < cutoff:
            truncated = True
            continue
        message = Event(data={"sender": sender}, event_id=str(row_id), timestamp=timestamp)
        messages.append(message)

    return EventBatch(
        events=messages, cursor=cursor, has_more=len(rows) > limit, truncated=truncated
    )
```

FastMCP runs synchronous readers in a worker thread and awaits asynchronous readers directly. It validates each event's data against the payload model and applies `for_subscription` before delivery. A reader can also use `poll.arguments` to narrow an upstream query. Give each occurrence its upstream ID so that reading the same row twice produces the same event ID.

`has_more=True` asks the client to read the next page immediately. `truncated=True` tells it that some history was skipped. The example assumes an append-only table and reports a gap when the requested age limit excludes a row. For an upstream that expires records, also report a gap when the cursor predates its retention window. The [Jetstream example](https://github.com/PrefectHQ/fastmcp/blob/main/examples/events/jetstream.py) shows how to work with an external service's replay window and time-based cursor.

### Subscription authorization

For poll and push, a reader can check the caller's authorization on each read. Webhook reads run in the sender after the subscribing client disconnects, so a reader that depends on the original request context cannot use that check for background deliveries. Subscription arguments express what the caller wants to receive. A reader can raise `MCPError` from `mcp.shared.exceptions` with the extension's `Forbidden` code (`-32024`) to reject the request. On an open stream, `Forbidden`, `NotFound`, or `Unsupported` ends the subscription and the client raises the error. Other mid-stream reader errors are reported and the server reads again on the next interval.

## Deployment

Register Events on the server clients connect to directly. Mounting a server or proxying it does not forward its event types.

### Event retention and replicas

By default FastMCP keeps the last 1,000 emitted events per type in memory. Set `EventsExtension(emit_buffer=...)` to change the limit. Each server process has its own buffer. Restarting that process clears it, and a client polling a different replica reads a different log. In either case a cursor from the previous buffer produces a gap.

Use `DocketEventLog` when multiple replicas need to serve the same emitted events or when clients must resume after a server restart. Install the Docket extra on the server and point each replica at the same Redis database and log name.

```bash
pip install "fastmcp[events]" "fastmcp-events[docket]"
```

```python
from fastmcp import FastMCP
from fastmcp_events import EventsExtension
from fastmcp_events.docket_log import DocketEventLog

log = DocketEventLog("redis://localhost:6379/0", name="builds", max_events=10_000)
events = EventsExtension(log=log)
mcp = FastMCP("Builds")
mcp.add_extension(events)
```

A build emitted on one replica can now wake a stream on another. Redis trims each event type's stream approximately to `max_events` and a cursor stays usable across server restarts while Redis retains that history. Pass `docket=` to reuse an open Docket instance. A shared `memory://` URL also works for testing within one process.

### Webhook senders across replicas

Webhook delivery keeps two kinds of state. The event log holds the builds themselves. The webhook store holds callback registrations, signing secrets, lease deadlines, and delivery positions. Both default to process memory. For a replicated build server, share the event log as above and give each replica the same subscription store, for example `WebhookDelivery(store=RedisStore(url="redis://localhost:6379/0"))` using `RedisStore` from `key_value.aio.stores.redis`. For a reader-backed event type, each replica needs access to the same upstream history.

On hosts that can only run work during a request or a scheduled invocation, set `WebhookDelivery(sender=False, store=...)`. Have a scheduled worker with the same registrations and stores run `await events.deliver_webhooks()` to make one delivery pass.

### Routing headers

An HTTP gateway can route a subscription by one of its arguments. For example, annotate the `repo` parameter of `for_subscription` with `Annotated[str, Field(json_schema_extra={"x-mcp-header": "Repo"})]` (from `typing` and `pydantic`, respectively). A client subscribing with `repo="api"` then sends `Mcp-Param-Repo: api` on each poll or stream request. Choose a value that can be visible to intermediaries.

FastMCP checks the event name and annotated arguments against the HTTP headers. A mismatch returns the JSON-RPC error `HeaderMismatch` (`-32020`) in an HTTP 200 response. The subscription client refreshes its event listing and retries once with the current header schema.
